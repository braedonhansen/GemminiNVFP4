# M6.5: multi-tile NVFP4 matmuls, bit-exact in Spike and Verilator (the first working version)

Date: 2026-10-20. Gemmini `nvfp4` (local, never pushed) at `b800fd68`, libgemmini `nvfp4` at `9555cda`; rocc-tests `350547f` plus untracked `nvfp4_*` files and the Makefile list lines. **No RTL or model change was needed**: every shape passed on the first run. Evidence: `logs/m6.5.steps`, `logs/m6.5-*`.

## Test program
`hw/tests/nvfp4_e2e_mnk.c` is `nvfp4_e2e.c` generalised: sizes come from the data header (`E2E_M/N/K`), one wrapper per shape (`nvfp4_mt_m<M>n<N>k<K>.c` defines `E2E_DATA_HEADER` and includes it). The multi-tile work is done by the existing `gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, ...)`: no tile is unrolled in software. Layout: A tiles at spad row 0 (i-major), the FP32 output at `BANK_ROWS` (row 4096), B at the top (the loop takes B's end address), accumulator rows `tiles_I*tiles_J*16`. `_Static_assert`s check, from `gemmini_params_nvfp4.h`: A + B + C rows fit the 16,384 spad rows and do not overlap, accumulator rows <= `ACC_ROWS` (512), scale bytes per operand <= 4096. The largest shape uses A 1024 + B 1024 + C 1024 spad rows and 64 accumulator rows; the scale memory holds 2048 B per operand.

`refmodel/export_e2e.py [path [seed [M N K]]]` repeats the zero/subnormal scale corners in every 32-row / 32-column tile, and for multi-tile shapes forces one output per tile pair to be a `-0` without the "+0 + blk" first write (zero-scale A row 32t+3 holding -1.0, B column 32u+13 holding +1.0). The export asserts at least one such output; `refmodel/tests/test_export_e2e.py` checks every tile has one, and that all 7 committed headers (the original three and the four new ones) regenerate byte-identically from their seeds (pytest: 145 passed).

The comparison is on every FP32 output bit pattern against the refmodel, so Spike, the RTL and the refmodel agree on all 14,336 outputs. The Verilator store addressing (chunk stride, j-group, row tile, row step from `docs/M6.3C-integration.md`) is now confirmed for N tiles, M tiles and both.

## Not covered
- Shapes with M or N not a multiple of 32 or K not a multiple of 16 (no padding path; the loop's padding arguments are 0), and shapes beyond the scratchpad or accumulator capacity (the largest here uses 64 of 512 accumulator rows and 3,072 of 16,384 spad rows plus the B region).
- Only one K accumulation order (kb ascending), which the hardware and the model fix.
- Not run: accumulation across separate loop calls (`ex_accumulate`), ReLU or other activations on the FP32 output, the bias (`D`) input, transposed A or B, the double-buffered and concurrent-loop paths, and a direct accumulator-to-DRAM FP32 mvout (still the spad route).
- The scale memory window of 4096 B per operand (M or N times K/16) caps one loop call, e.g. M = 128 with K = 512 would not fit.
- Control (a) was run in Spike only; (b) and (c) mutate the j-group term only. The row-tile and row-step terms are exercised by shapes 1 and 3 passing, but were not mutated.
- Timing: cycle counts include setup and the spad-to-DRAM copy; nothing was optimised or compared with the MX base.
- No synthesis of the new datapath (the 32-lane mvout multiplier is still unserialised).
