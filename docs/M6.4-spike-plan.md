## 1. How the MX model works (D1 map)
| what | where (MX base = same lines as the branch minus the NVFP4 insertions above them) | note |
|---|---|---|
| entry | `mx_loop_ws_spad` (`gemmini.cc:1404`); DRAM-C variant `mx_loop_ws_dram` (`:1329`) calls it with `mx_dram_out` | FP4 x FP4 quad path = the `if (actf == 2)` branch (`:1863`) |

| per-row precision ramp | `acc_e/acc_m` table (`:1448-1457`): rows 0-7 E4M4, 8-9 E4M5, 10-14 E4M6, 15 BF16; `fp_quantize_rne`/`fp_add_exact` per K step (`:1968-1975`) | this is the "MX precision ramp"; NVFP4 does not have it (exact integer sum) |

| tensor factor | MX has none | |

## 2. Build selection (I4)
`-DGEMMINI_NVFP4` selects the model. `Makefile:23-27` adds `libgemmini_nvfp4.so` (compiled with `-ffp-contract=off`), included in `default` and `install` (`Makefile:9,34-35`). `gemmini.cc:21-24` registers the extension as `gemmini_nvfp4`; the instruction handler keeps looking itself up as `"gemmini"` because `gemmini_t::name()` (`gemmini.h:169`) returns `"gemmini"` in every variant (the same reason the DIM=32 / DIM=8 builds work). All NVFP4 code is under `#ifdef GEMMINI_NVFP4` (`gemmini.cc:3-5,21-24,1424-1432,1864-1934`), so the default and DIM variants preprocess to the same translation unit as before (proved in D6).

## 3. One NVFP4 change per RTL behaviour
| # | RTL behaviour (doc, file:line on Gemmini `nvfp4`) | model counterpart (NVFP4 build) |
|---|---|---|
| 1 | Operand layout: A in the MX FP4 quad layout, B nibble-packed, same spad addressing, same loop order i fastest, then j, then k (M6.3B "B3", `ExecuteController.scala:1230-1243`) | same unpack and loop nest as the MX FP4 branch: `gemmini.cc:1883-1893`; tile addresses `:1879-1880` |
| 2 | `NvFp4PE`: E2M1 products as doubled integers (0,1,2,3,4,6,8,12), exact `SInt(13)` column sums over the 16 K rows of one tile; no precision ramp (M6.2 A, `NvFp4PE.scala`) | `nvfp4::e2m1_int2` (`nvfp4_math.h:25`); `isum += a[r]*b[c]` over `kk < 16` in `int32_t` (`gemmini.cc:1892-1894`) |
| 3 | Scale block = 16 elements = one K tile, `scaleSize = 16`, `tilesPerMxBlock = 1`, `kScaleShift = 0`: pass `(k, j, i)` reads A-scale row `bound_i*k + i`, B-scale row `bound_j*k + j` (M6.3B "B3") | scale row is `k_outer` (no `/GROUP`): `a_off = act_sel*4096 + k_outer*M_DIM + row`, `b_off = wgt_sel*4096 + k_outer*N_DIM + col` (`gemmini.cc:1899-1900`); the byte layout `A_sc[K/16][M]`, `B_sc[K/16][N]` is what `mx_load_scales` already stores linearly |
| 4 | `NvFp4ScaleStage`: exact E4M3 x E4M3 x isum -> FP32, NaN scale code -> canonical qNaN `0x7FC00000`, IEEE sign rules for zero (M6.3A, `refmodel/scale_stage.py`) | `nvfp4::scale_stage` (`nvfp4_math.h:40`): `(float(isum)*sA)*sB` in the refmodel's order; both factors and the product are exact in float32, so no rounding can occur; `e4m3_decode` (`:33`) |
| 5 | FP32 accumulate: IEEE FP32 in the accumulator SRAM, one `Fp32AccAdd2` add per K block, K ascending, RNE (M6.3B pipeline `acc_latency = 6`) | `nvfp4::f32_add` (`:47`) on the stored bit pattern; the accumulator lives in `mx_smem` as two `uint16_t` per element, row-major `[M][N]` (`gemmini.cc:1869,1904-1909`) |
| 6 | First write of a pass is `+0 + blk` through the adder, not a direct store, so a `-0` block becomes `+0` (M6.3C `NvFp4RmwPipe.scala:77,86,97`) | `nvfp4::acc_update(first, prev, blk)` (`:52`), `first = (k_outer == 0 && !ex_accumulate)` (`gemmini.cc:1907`). With `ex_accumulate` the previous stored FP32 is added (RTL: accumulate into the SRAM row) |
| 7 | Tensor factor at mvout: 2-stage RNE `Fp32Mul2` on all lanes, factor = FP32 `acc_scale` from CONFIG_ST rs2[63:32]; `ACC_SCALE_IDENTITY` must be a real factor (M6.3C "Tensor scale") | `nvfp4::f32_mul(acc, bits(acc_shift))` (`gemmini.cc:1915-1925`); `acc_shift` is set by the unchanged config_mvout handler (`:540`). The accumulator keeps the unscaled value; only the stored copy is scaled (as in RTL: scaling is on the read path) |
| 8 | FP32 store layout through the scratchpad: row-major, 4 FP32 per 16-byte spad row, 8 consecutive spad rows per 32-column output row; software copies spad rows to DRAM with ordinary mvouts (M6.3C "Store path") | bytes `4e..4e+3` of element `e = r*N_DIM + c` go to `spad[C_spad + k/DIM][k%DIM]`, little-endian (`gemmini.cc:1917-1932`); the spad vector is grown as needed |
| 9 | NVFP4-only datapath: no other formats, no LUTs (M6.2 option iii) | guard at `gemmini.cc:1424-1432`: anything but FP4 x FP4 quad, `out_fmt = 3`, no altfmt/LUT, no DRAM-C loop prints a message and does nothing |

## 4. Not modelled (flagged, same open items as the RTL docs)
- ReLU / other store activations on the FP32 output (RTL path untested; the MX BF16 ReLU is not applied).
- Direct accumulator -> DRAM FP32 mvout, bias through accumulator mvin (`has_acc_mvin = false` in the RTL), multi-tile M/N output addressing (RTL derived, not run: the model writes plain row-major `[M][N]`).
- Unloaded scale bytes keep the MX default `0x7f`, which is an E4M3 NaN (RTL: undefined SRAM content).
- Timing: the perf model (`gemmini_perf.cc`) is unchanged and not NVFP4-aware; the reported 179 cycles are the MX-style model's, not the RTL's 2,555.
