# M7.P1: power-job packages for the five designs

Date: 2026-10-30. Status: **five job tarballs built and checked locally; none has run on the server.** Nothing here contacted the server.
Step log: `logs/m7p1.steps`. Flow: `hw/power/genus_gemmini.tcl`, `joules_gemmini.tcl`, `run.csh` (the M7.P0 versions that ran for job `int8-stock-a` are kept in `hw/power/p0/`).

## What every job contains
Genus (default flow, 5.0 ns clock, hierarchy kept) then Joules (RTL VCD of the kernel window rescaled to 5 ns, gate netlist), with
**Nangate45 typical `.lib` + the OpenRAM `*_pj.lib` banks of that design** (the P0b kit). The design RTL is the unmodified `gen-collateral` set reachable from `Gemmini`;
exactly one `wrappers/<design>/` folder supplies the `*_ext` SRAM modules, which instantiate the OpenRAM bank cells (liberty cells = hard macros).
All parameters sit in the job's `window.csh`. Job contents: `rtl/`, `filelist.f`, `wrappers/`, `lib/`, `window.csh`, `groups.tcl`, `macro_instances.txt`, `extract.json`, `act/kernel.vcd.gz`, `MANIFEST`.

## Common workload
M=64, N=64, K=512 (2,097,152 MACs). A and B come from `accuracy_sweep.make_inputs("gaussian", 512, seed 20261030, 64, 64)` for **every** design
(`refmodel/export_m7p1.py` prints sha256(A)=514a005e992c89d9, sha256(B)=860d5669a945ca6d of the float64 bytes), then each design's own M7.A Level-H recipe and software path.
Tests: `hw/tests/m7p1_{int8,fp32,mxfp4,mxfp8,nvfp4}.c` (+ `_data.h`). Each prints `M7P kernel start/end` (the window starts at the first RoCC command after the marker and ends at the last `io_busy` fall) and has a `-DM7P1_CTL` control that flips one output bit.

## What each design writes back, and what differs between designs
| Design | Software path | Output | Expected model |
|---|---|---|---|
| INT8 | `tiled_matmul_auto`, WS, `full_C` | INT32, row-major in DRAM | exact integer matmul (bit-exact) |
| FP32 (DIM 4) | `tiled_matmul_auto`, WS | FP32 | **fused multiply-add** `hw_models.fp32_fused_h` |
| MXFP8 / MXFP4 | `m7a_mx` style: MX_LOAD_SCALES, mvin, one `loop_ws_spad`, flat mvout of the scratchpad result | BF16 | `mx.hw_matmul` (bit-exact) |
| NVFP4 | `nvfp4_e2e_mnk` path: MX_LOAD_SCALES, quad-layout mvin, `loop_ws_spad`, tensor scale in `acc_scale`, scratchpad FP32 readback | FP32 | `hw_dot.hw_matmul_v0` (bit-exact) |

Differences to keep in mind when comparing energy:
- **FP32 RTL is fused, not the M7.A "separate" model.** The RTL matches the fused model on all 4096 outputs and differs from the separate model in 2841. M7.A's FP32 Level-H headline used the separate model (Spike-verified, but Spike is not the RTL); this is the first RTL evidence and the `fp32_fused` ablation row is the one that describes the hardware.
- **Array size and window length:** FP32 is DIM 4 (139,329 cycles), the others DIM 16 (13k to 28k). Per-MAC energy is the like-for-like metric, as in the measurement plan.
- **Scale and operand traffic differ by design** (INT8: none; MX: 1 B scale per 32 along K; NVFP4: 1 B per 16 plus two tensor scalars). The MX and NVFP4 software issue more RoCC commands (171 to 299 versus 11 for INT8, whose loop unroller works inside Gemmini); the window counts all of it.
- **The kernel window includes the mvins and the mvouts** of each design's own software path, but not Rocket's work (CPU-side data setup and the check). The NVFP4 and MX FP4/FP8 results leave the accumulator through the scratchpad and are copied to DRAM by mvouts inside the window.
- **VCD scope:** the Gemmini instance is `gemmini` in the stock tree and `v` in the MX/NVFP4 trees; `window.csh` has the right `DUT` for each job.
- **The Chisel configs ship TL monitors inside Gemmini** (5 files in INT8, 12 in NVFP4); their bodies sit under `ifndef SYNTHESIS`, which the Genus script defines.
- INT8 uses the same operands and shapes as the others now; job `int8-stock-a` used xorshift data, so a and b are not comparable in data.

## Risks for the first server runs
1. **Libraries never read by Genus/Joules:** Nangate45 and the OpenRAM `_pj.lib` (bus types, `pg_pin`, `memory()` groups). First look at `reports/genus.out` for `read_libs` errors.
2. **Bank-cell check:** `get_db insts -if ".base_cell.name == ..."` is unverified; if it fails the script falls back to parsing a written netlist, and stops with `M7P-FAIL` if neither agrees. Netlist instance line format is assumed.
3. **Wrapper logic synthesised, banks fixed:** if Genus ungroups or renames the wrappers the macro check fails early (minutes, not hours).
4. **Size:** `mxfp8-a` is 1.26 GB (VCD 4.9 GiB raw, 115,559 timestamps, 337 M changes) and `fp32-stock-a` 0.72 GB (3.8 GiB raw): upload time, home-directory quota, and Joules read time/memory are unknown. If Joules cannot read the full window, `-start/-end` can select a sub-window (energy then scales by window length).
5. **Run time:** int8-stock-a took about 2 h 40 min for 907k cells; NVFP4 and MX arrays are larger (the Yosys run on the MX array did not finish in 12 GB), so expect longer Genus runs. FP32 is the smallest design.
6. **Timing:** 5.0 ns was never checked for the FP32 hardfloat and the MX/NVFP4 accumulators; the first `timing.rpt` decides (change the clock for all designs together).
7. **SRAM activity:** the VCD comes from Chipyard's behavioural SRAM, so bank `csb` pins are driven only by propagation from the macro ports through the wrapper decode; check bank power in `power_inst_*` of the wrapper instances against `N_access x E` from `energy_table.md`.
8. **Window rescale:** timestamps are multiplied by 2.5 (2000 ps simulated to 5000 ps); dynamic energy is independent of it, average power and leakage energy are not.
9. SRAM leakage and read=write energy are placeholders (P0b section 4).
