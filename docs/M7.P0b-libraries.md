## 3. OpenRAM settings and compositions (L3)

Common config: `tech_name = "freepdk45"`, `netlist_only = True`, `analytical_delay = True`, `nominal_corner_only = True`
(TT, 1.0 V, 25 C), `use_conda = False`, `route_supplies = False`, `check_lvsdrc = False`. No SPICE, no layout, no PDK files.
Each run was started from OpenRAM's own directory with `OPENRAM_HOME`/`OPENRAM_TECH` set as in its `setpaths.sh`. Configs are in
`openram/configs/`, run logs and `time -v` output in `openram/logs/`.

**Why composed from banks instead of one big macro.** The direct 4096 x 128 run (524 kbit) was killed by my 900 s limit after
15 minutes. Profiling a smaller case showed why: OpenRAM's `net_spice.connect_pin` checks `pin in self.pins` on a Python list,
and the supply nets collect a pin from every bit cell, so netlist build time grows with the square of the total bit count:

| Test macro | bits | netlist time |
|---|---|---|
| 64 x 32 | 2 k | 1.8 s |
| 256 x 32 | 8 k | 25 s |
| 512 x 32 | 16 k | > 100 s (timeout) |
| 256 x 128 (1RW, final) | 32 k | 6 min 49 s |

So the macros are built from banks of 16 to 32 kbit. I did not patch OpenRAM; the brief says to compose.
All five designs need only five distinct banks:

| Bank (module name) | Shape | Ports | Write mask | Used for | Run time | Peak RSS |
|---|---|---|---|---|---|---|
| `bk_1rw_256x128_ws8` | 256 x 128 | 1RW | 8 b (16 bits) | INT8/FP32 scratchpad | 6:49 | 262 MB |
| `bk_1w1r_256x128_ws8` | 256 x 128 | 1W+1R | 8 b (16 bits) | MX/NVFP4 scratchpad, FP32 accumulator | 7:18 | 313 MB |
| `bk_1w1r_64x512_ws8` | 64 x 512 | 1W+1R | 8 b (64 bits) | INT8 accumulator | 8:05 | 336 MB |
| `bk_1w1r_64x512_ws256` | 64 x 512 | 1W+1R | 256 b (2 bits) | MX/NVFP4 accumulator | 7:39 | 335 MB |
| `bk_1w1r_128x128_nomask` | 128 x 128 | 1W+1R | none | MX/NVFP4 scale memory (direct, no composition) | 1:54 | 221 MB |

Peak memory over all runs: 336 MB (limit 3 GB). One OpenRAM job at a time. Because the banks are shared, the other designs' macros
(MXFP8, FP32) needed no extra OpenRAM runs: they reuse these banks, which also covers the "configs for the other designs" item of L5.

Compositions (wrapper = `tools/gen_wrappers.py`; bank row chosen by the high address bits, others get `csb` high):

The wrapper adds a registered read-select (4 flops for the 16-bank cases) and a 16:1 (or 8:1, 4:1) read mux per data bit. They are
ordinary logic, so synthesis counts their area and power. This is the "one bank row active per access" accounting.

**Checks run (all on the staged files):**
- every bank has `.lib` and `.v`; `tools/check_macro_libs.py` printed 10 PASS lines (5 raw + 5 `_pj` libs): braces balanced, one `cell()` whose
  name equals the Verilog module, leakage > 0, read and write internal power > 0, disabled states = 0 in the `_pj` libs, every Verilog port present as a lib pin;
- `tools/port_diff.py`: wrapper port lists against the Chisel declarations in `top.mems.v`: INT8 2/2, MXFP4 3/3, NVFP4 3/3 identical in name, direction and width
  (`verify/port_diff.log`). Negative controls: a renamed port gave `DIFFER` (rc 1) and an empty directory gave `compared=0` (rc 1);
- functional simulation (Verilator `--binary --timing`, `tools/tb/`): each of the 10 wrapper files (INT8 2, MXFP4 3, NVFP4 3, FP32 2) did 4000 random masked write/read
  cycles against a behavioural reference using the OpenRAM `.v` bank models: 1527 to 2686 read checks each, 0 errors (`verify/wrapper_sim.log`).
  Negative control: reading the select bits from the wrong address bits gave 140 errors. MXFP8's three wrappers are byte-identical to MXFP4's except for a header line, so they were not simulated separately.

## 4. Energy and leakage (L4)

### What OpenRAM's analytical lib really contains (and the three fixes)

1. **Units.** The clock-pin `internal_power` numbers are an average *power in mW at `default_event_frequency = 100 MHz`*
   (`power_dyn = C * Vdd * Vswing * f`, then `/1e6`), but Liberty reads them as energy in V*mA*ns = pJ. So a value of 4.887 means
   4.887 mW / 100 MHz = **48.9 pJ**, not 4.9 pJ. `tools/fix_lib_power.py` multiplies by 10 (divides by 0.1 GHz).
   Evidence that the x10 is right: read as pJ, the raw numbers would be 0.019 to 0.066 pJ/bit, 3 to 10 times below any 45 nm SRAM figure; with the fix they land at 0.19 to 0.66 pJ/bit.
2. **Disabled state.** All four `when` states (read, write, and the two with `csb` high) carry the same value, so a deselected bank would burn a
   full access every cycle. The `_pj` libs set the `csb`-high states to 0. Without this the "one bank active" accounting would not hold.
3. **Rise/fall.** `rise_power` and `fall_power` are equal, which would charge each cycle twice. The `_pj` libs put the whole access energy on `rise_power` and 0 on `fall_power`.

Leakage and all timing tables are untouched. **Load the `*_pj.lib` files for power runs.** The raw `.lib` files are kept for reference only.

### Expected-range note and flags

Reference values are from memory of the literature and were **not re-checked in this session** (no literature download was allowed):
Horowitz, ISSCC 2014, 45 nm, 64-bit read: about 10 pJ for 8 KB and about 20 pJ for 32 KB, i.e. roughly 0.15 to 0.3 pJ/bit for small macros.
6T leakage at 45 nm spans roughly 0.1 to 10 nW/bit depending on the threshold-voltage flavour and temperature.

| Quantity | This kit | Expected | Verdict |
|---|---|---|---|
| Access energy per bit, 64 x 512 banks | 0.19 pJ/bit | 0.15 to 0.3 | in range |
| Access energy per bit, 256 x 128 and 128 x 128 banks | 0.36 to 0.66 pJ/bit | 0.15 to 0.3 | 1.2 to 4x high, within 10x |
| Leakage | 1.03 to 1.09 nW/bit | 0.1 to 10 | in range, but see below |
| Raw (uncorrected) lib read as pJ | 0.019 to 0.066 pJ/bit | 0.15 to 0.3 | 3 to 10x too low, which is why the units fix is needed |

Nothing is off by more than 10x after the fixes. Flags, in order of importance:
1. **Leakage is a placeholder.** `technology/freepdk45/tech/tech.py` sets `bitcell_leakage = 1` nW and `inv_leakage = nand_leakage = dff_leakage = 1` nW, all generic constants, not SPICE-extracted. The results are 1.03 to 1.09 nW/bit because the bit cells dominate. It is the right order of magnitude, but treat SRAM leakage as +/- 5x. It is identical for all designs per bit, so differences between designs follow capacity only.
2. **Read energy equals write energy** in the analytical model; real writes cost more (full bit-line swing). Write-heavy phases (mvin, accumulate writes) are underestimated.
3. **Bank aspect ratio moves the result by up to 3.5x** (0.19 versus 0.66 pJ/bit at equal capacity). The compositions fix the shape per macro, and the same bank is used for the same role in every design, so cross-design comparisons are consistent, but absolute SRAM energy is only good to about 3x.
4. **No layout, so no wire parasitics**: with `netlist_only` the bit-line and word-line wire lengths are 0; only the drain/gate capacitances of the cells count. This pushes energies down; the 0.7 fF drain term per row is a coarse substitute.
5. **Port type matters and is real**: the 1W+1R banks cost 1.7x more per access than the 1RW bank of the same shape (84.8 versus 48.9 pJ). This favours INT8 (1RW scratchpad) over the MX/NVFP4 scratchpads (1W+1R) by construction of the elaborated designs, not of the library.
6. **Macro area is 0** in the bank libs (`area : 0;`, no LEF): area reports must add SRAM area separately.
7. Typical corner only (TT, 1.0 V, 25 C); no process/temperature scaling.

The numbers are analytical estimates meant for comparing designs on the same footing, not absolute silicon predictions.

## 5. Loading the kit in Genus and Joules (L6)

Files, relative to the unpacked `freepdk45/` directory:

```tcl
set K  <path>/freepdk45
set_db init_lib_search_path [list $K/nangate45 $K/openram/banks]
set_db library [list \
   NangateOpenCellLibrary_typical.lib \
   bk_1rw_256x128_ws8_pj.lib bk_1w1r_256x128_ws8_pj.lib bk_1w1r_64x512_ws8_pj.lib \
   bk_1w1r_64x512_ws256_pj.lib bk_1w1r_128x128_nomask_pj.lib ]
# (or read_libs with the same list; only the banks a design uses are needed, but loading all five is harmless)
```

Verilog:
- Read **the design's RTL** (the Gemmini module tree from `gen-collateral`) **plus `wrappers/<design>/*.v`**.
- Do **not** read Chipyard's `*.top.mems.v` (it holds flop-array versions of `mem_ext` etc.) and do **not** read `openram/banks/*.v`. Those are
  OpenRAM simulation models with `#` delays and `$display`; synthesis must treat the `bk_*` cells as library black boxes. The bank cells are
  marked `dont_use`, `dont_touch`, `map_only` in the lib, so they are only ever instantiated, never inferred.
- `wrappers/mxfp8` and `wrappers/fp32` come from derived inventories; do not use them as the final answer for those designs until the
  matching configs are elaborated and `tools/port_diff.py` is run on them.
- The wrapper modules keep the Chisel module names (`mem_ext`, `mem_0_ext`, `banks_0_ext`, `banks_0_0_ext`). Their names collide across designs,
  so load exactly one `wrappers/<design>/` folder per run.

Power (Joules):
- Clock-pin internal power of each bank is charged only in the state `!csb0 & ...` (or `!csb0` / `!csb1` for 1W+1R), i.e. when the wrapper selects that bank. For a
  gate-level or RTL-with-wrapper activity run, annotation of `csb*` therefore gives the one-bank-per-access energy automatically.
- If activity comes from the Verilator RTL run (which has Chipyard's own `mem_ext`, not the wrapper), bank-level `csb` does not exist in the
  waveform. Use access counts instead: `E_sram = N_read * E_read + N_write * E_write + P_leak * T`, with the per-macro numbers in section 4, counting
  `en & !wmode` / `en & wmode` for 1RW and `R0_en` / `W0_en` for 1W+1R at the `*_ext` ports. The wrapper's select flops and read mux still come from Genus/Joules.
- Leakage comes straight from `cell_leakage_power` in each lib (mW; Nangate's own unit applies to the standard cells).

## 6. Limitations

- Analytical model only, typical corner, no layout parasitics, no SPICE characterisation (section 4 flags).
- The kit has never been read by Genus/Joules. Likely first issues, if any: `type (data)` bus definitions in the OpenRAM lib, the `pg_pin` blocks, `memory()` groups.
- Bank `.v` models read `dout` at `negedge + 3 ns` and set it to X for 1 ns after each posedge, so a simulation must sample `rdata` before the next posedge (the testbench does, 1 ns early).
- MXFP8 and FP32 macro shapes are derived, not elaborated (section 2). Elaborating `MxE4M3OnlyGemminiRocketConfig` (MX tree) and `FPGemminiRocketConfig` (stock tree) and re-running `port_diff.py` closes this.
- Large intermediate files (SPICE netlists, 2.5 MB each) stay in `~/nvfp4-logs/m7p-lib/gen/`; nothing in the kit exceeds 20 MB.
