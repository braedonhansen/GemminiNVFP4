## 1. MX semantics (confirmed from code)

### 1.1 Pairing: two FP4 per byte, lane k = act[k/2] x wei[k%2]
- A spad/mesh element is one **byte = two FP4 codes** (`inputTypeProjected = MxFloat(2,2,2)` = 8 bits, `ConfigsFP.scala:263-264`).
- On the direct (non-LUT) read path the byte is expanded `Cat(byte(7,4), byte(3,0))` into two slots, so **element 0 = low nibble, element 1 = high nibble** (`Controller.scala:998-999`). The same function serves activations and weights.
- A PE multiplies the two activation elements by the two weight elements as an outer product. `MxPE.scala:34`: "4-output: lane k = act(k/2) x wei(k%2) -> [a0w0,a0w1,a1w0,a1w1]"; implemented at `MxPE.scala:38-51` (`actIdx = k/2`, `weiIdx = k%2`). The core splits the bus the same way: `lanes2_a = in_activation.asTypeOf(Vec(2, ...))`, element 0 = LSBs (`mxgen/MxFpMulCore.scala:106-109`).
- So the two activation nibbles are two **different output rows (M)** and the two weight nibbles two **different output columns (N)**. K is **not** packed; one mesh row = one K index.
  - libgemmini confirms the memory layout: for the FP4 activation "byte (m/2, n) = row m even low nibble" (`libgemmini/gemmini.cc:1160-1161`) and the matmul model reads `nib = (m & 1) ? byte>>4 : byte&0xF` for A (`gemmini.cc:1867-1870`) and `(n & 1) ? ... ` for B (`gemmini.cc:1872-1878`).
  - The rocc-test confirms the tiling: `tiles_I = M/DIM/2`, `tiles_J = N/DIM/2`, `tiles_K = K/DIM` (`gemmini-rocc-tests/bareMetalC/matmul_tiled_fp4_64x64.c:84-86`); A is mvin'd with one byte per K position and B with `ld stride N/2` bytes (lines 106-123).
  - One mesh pass therefore computes a **32 (M) x 32 (N)** output tile for a **K = 16** slice (`TM = 2*DIM`, `TN = 2*DIM`, `gemmini.cc:1851-1852`).
- Output lanes: the 4 lanes per mesh column are packed back into accumulator rows as `row0 = lanes {0,1}` (even M), `row1 = lanes {2,3}` (odd M) (`ExecuteController.scala:1236-1247`).

### 1.2 Flow and structure (weight-stationary, `tileRows = tileColumns = 1`, 16 x 16)
- **PE** (`PE.scala:36-167`): `in_a` (activation) passes straight through (`:92`); `in_b` is the partial sum from above; `in_d` is the weight preload. Weights live in a double buffer `c1/c2` (`:82-83`). WS branch (`:138-151`): with `prop == PROPAGATE`, `c1 := d` and the MAC uses `c2`; with `prop == COMPUTE`, `c2 := d` and the MAC uses `c1`; `out_c` is the buffer being loaded; `out_b = mac_unit.out_d` (combinational). When `!valid` the registers hold (`:161-165`). The MAC is `mac_mx` -> `MxFpMul` (`PE.scala:28`, `Arithmetic.scala:615-659`).
- **Tile** (`Tile.scala`): a purely combinational array of PEs; with 1x1 tiles it adds nothing.
- **Mesh** (`Mesh.scala`), one hop = `L = tile_latency + 1` registers (`tile_latency = 1` in `defaultMxFPConfig`, `ConfigsFP.scala:287`, so **L = 2**; stock Gemmini has L = 1):
  - activations flow **west -> east** (`:102-114`), partial sums **north -> south** (`:117-130`), weights preload **north -> south** (`:133-145`), `propagate`/`shift` follow the column (`:149-159`), `valid`/`id`/`last` too (`:162-186`);
  - bottom row feeds the outputs through `ShiftRegister(..., output_delay)` (`:190-198`, `mesh_output_delay = 0`).
- **MeshWithDelays** (`MeshWithDelays.scala`, header says "DO NOT TOUCH") does the skew/de-skew: `in_a` row r delayed `r*(L)`, `in_b/in_d/valid/propagate` column c delayed `c*L` (`shifted()` `:78-99`, `:201-203`, `:209-219`); outputs de-skewed with `shifted(mesh.io.out_b, outBanks, reverse=true)` (`:232`). `req.pe_control.propagate` toggles every request (`in_prop`, `:116, :124`), so consecutive requests alternate c1/c2.
- **Timing of a pass** (derived, and reproduced bit-exactly by `NvFp4MeshSpec`): feed step m of the 16 steps of a request at cycle `base + m`; in_a(r) at `base+m+r*L`, column inputs at `base+m+c*L`; output of step m, column c is visible at `base + m + c*L + 16*L`. Weight preload uses the same request: d slot m carries weight row `15-m` (PE row r ends up holding row r). A request's preload overlaps the previous request's compute, and the weights are latched exactly in time for the next request (no bubble).
- **Partial-sum type.** Each mesh row has its own accumulator precision (`Mesh.scala:55`, `meshAccPrecisionList`): significand 5 (rows 0-7), 6 (8-9), 7 (10-14), 8 (row 15), exponent 4/8 (`ConfigsFP.scala:271-276`); the partial sum is resized per hop (`Mesh.scala:121`). Product precision is (4,4) (`:271`). libgemmini mirrors this ramp (`gemmini.cc:1429-1441`) and per-step quantizes product and accumulator (`:1881-1888`).

### 1.3 What `NvFp4Mesh` matches and where it differs
| Aspect | MX | `NvFp4Mesh` |
|---|---|---|
| Pairing, nibble order, lane order | as above | identical (`a0w0,a0w1,a1w0,a1w1`, low nibble = element 0) |
| Flow directions, c1/c2 double buffer, propagate, valid gating | `PE.scala`, `Mesh.scala` | same structure, same register counts per hop (`tileLatency` parameter, `L = tileLatency+1`) |
| Skew/de-skew | `MeshWithDelays` | **not included**; the testbench applies exactly MeshWithDelays' skew. Drop-in is at the `Mesh` level (section 3) |
| Partial sum | per-row FP ramp, recoded BF16-like lanes | `Vec(4, SInt(13))`, exact |
| Control sidebands (`shift`, `dataflow`, `id`, `last`), mx format/mode inputs | present | dropped (not needed in an NVFP4-only mesh); `propagate` and `valid` kept |
| Per-bit input gating by format (`Mesh.scala:105-139`) | present | none: FP4 only |
| OS dataflow, tree reduction, tiles > 1x1 | supported | not modeled (WS, 1x1 tiles) |

## 2. Verified results of Phase A1 (summary; details in `hw/nvfp4pe/RESULTS-mesh.md`, `logs/m6.2.steps`)
- `NvFp4Mesh` (`hw/nvfp4pe/src/main/scala/nvfp4pe/NvFp4Mesh.scala`) is bit-exact against the refmodel integer block sums: DIM=4 13,248 outputs (207 passes) with `tile_latency` 0 and 1 and idle gaps; DIM=16 34,816 outputs (34 passes: the 67 refmodel blocks, +/-2304 extremes, zeros, -0, alternating signs, random) and 12,288 more at `tile_latency 1` with gaps; 0 mismatches. Negative controls (carry-in dropped in `addFold`; c1/c2 select flipped) fail every test.

## 3. Integration options

Common facts that shape every option:
- The Gemmini generator is parameterized by an `Arithmetic[T]` type class and the MX path is hard-wired to `MxFloat` and to `use_mx_scaling` (ScaleFactorMem, requantizer, 64-bit accumulator entries = 4 BF16 lanes).
- **D4 (FP32 accumulator) and D5 (`scaleSize = 16`) change things that MX modes depend on** (accumulator entry width and datatype, the ScaleFactorMem K-block mapping). Any option that keeps MX modes alive in the same build must therefore carry two accumulator datatypes and two scale-block sizes.

### (i) New NVFP4 mode inside `mac_mx` / `MxFpMul` / `MxFloat`
- Files: `mxgen/MxFPMul.scala` + `MxFpMulCore.scala` + `MxPE.scala` + `MxParameters.scala` (new `MxFormat`/`mxMode` for the integer product; **MxGen is a separate repo/submodule, `dba3e7e7`**), `Arithmetic.scala:615-659` (select mode), `Mesh.scala:55,121` (per-row `meshAccPrecisionList` resize would corrupt an integer lane carried in a recoded-float field; must be bypassed), `Mesh.scala:105-139` (bit gating by format), `ExecuteController.scala:1230`.
- MX modes: unchanged only if the new mode is elaboration-gated like the others (`MxConfig` already gates modes). Risk: highest, because the integer adder has to live inside the float `MxPEAddRecFN` lane datapath or bypass it, and `MxFpMul` returns recoded-float lanes (`rec_c`/`out`).
- Area: only the integer path is added, but the existing float add/normalize hardware remains in the same PE (it is what the V6 PE avoids).
- Spike: `gemmini.cc` MX loop model (`:1858-1904`) needs an NVFP4 branch; the ramp code stays for MX.
- Verdict: touches the most files in the most places (including another team's submodule) and keeps the biggest PE. Not recommended.

### (ii) Separate `NvFp4Mesh` instantiated beside the MX mesh, muxed by format
- Files: `MeshWithDelays.scala:187` (instantiate both; `MeshWithDelays` is marked "DO NOT TOUCH" but this is the only place the mesh is instantiated; the skew logic is reused unchanged for both) or one level up at `ExecuteController.scala:305-323`; new format code (e.g. `activation_mx_format = 3`) through `ExControllerMxScalingRegs`, `Controller.scala:943-1020` (FP4 expansion already generic), `ExecuteController.scala:1230-1261` (output select / packing), `MeshWithDelays.scala:229-236` (resp mux).
- MX modes: unchanged functionally if every NVFP4 signal is muxed off, but the output type of the two meshes differs (BF16-ish recoded lanes vs `SInt(13)` lanes), so the accumulator write path needs a second datapath (below) and, by D4, a second **accumulator datatype**.
- Area: sum of both meshes (MX FP4 array + NVFP4 array; numbers in section 5), plus a widened accumulator.
- Spike: add an NVFP4 branch next to the FP4 one (`gemmini.cc:1858-1904`).
- Verdict: the right shape if both formats must coexist (D8 comparisons need both, but they could also be two builds).

### (iii) Config-time swap: NVFP4-only build
- Files: `ConfigsFP.scala` (new `nvfp4MxFPConfig` modeled on `fp4OnlyMxFPConfig`, with `scaleSize = 16`, accType FP32, `meshAccPrecisionList` replaced), `Arithmetic.scala` (a new data type + `Arithmetic` instance, or an NVFP4 flag in `MxFloat`; the MX instance has stubbed `*`, `mac`, `>>`, `clippedToWidthOf`, `Arithmetic.scala:661-767`, so a new instance is mostly stubs), `MeshWithDelays.scala:187` (instantiate `NvFp4Mesh` instead of `Mesh` when the type is NVFP4; the same I/O ports are used: `in_a/in_b/in_d/propagate/valid -> out_b/out_valid`), `ExecuteController.scala:1230-1261`, `AccumulatorMem.scala` (scale stage and adder), `ScaleFactorMem.scala:196,227-230`, `LoopMatmul.scala:1106`, `Controller.scala:284-300` (QuantLut/requantizer checks).
- MX modes: removed from that build (the Berkeley config stays buildable, since every change is behind `config`/type tests).
- Area: smallest: NVFP4 mesh only, no float PE, no LUT/requantizer needed for FP4-direct.
- Spike: a separate libgemmini build/mode (`GEMMINI_*`-style define or runtime state bit); the MX FP4 model is untouched.
- Verdict: **recommended for the first working version (6.5).**

| | (i) in `mac_mx` | (ii) beside, muxed | (iii) NVFP4-only config |

## 4. The mesh-to-accumulator boundary (input to M6.3)

### 4.1 What MX does today
1. `Mesh.out_b(c)`: `Vec(tileColumns, outputType)`, `outputType = spatialArrayOutputType = MxFloat(8,8,4,true,false)` (`ConfigsFP.scala:269`): **4 lanes x recoded BF16 (17 bits)** = 68 bits per column. Before the bottom row each hop resizes to the row's ramp precision (`Mesh.scala:121`).
2. `ExecuteController.scala:1230`: `e.withWidthOf(accType)` converts recoded -> standard BF16 lanes (`Arithmetic.scala:727-750`), `accType = MxFloat(8,8,4)` = **64 bits per column entry**. The four lanes are then rearranged for the 2x2 pack (`:1236-1247`: row0 = lanes 0,1; row1 = lanes 2,3) and written with offset/mask (`:1259-1269`).
3. `AccumulatorMem.scala:211-252`: on `write.fire` it reads `ScaleFactorMem`, and one cycle later (`pipelined_writes(0)`) applies **`applyE9M0Scale`** to each BF16 lane (`:140-183`): the scale is a 9-bit sum of two E8M0 codes (`ScaleFactorMem.scala:227-230`), applied as an **exponent add with clamp**; no multiplier. The scaled data replace the write data at `pipelined_writes(1)` (`:259-262`) and feed `io.adder.op2` (`:276`).
4. The accumulate is `AccPipe` = `op1 + op2` using the type's `+`, i.e. a BF16 `MulAddRecFN` with RNE rounding (`AccumulatorMem.scala:77-85`, `Arithmetic.scala:666-719`).
5. `ScaleFactorMem` returns `combined_scales`: per column entry 4 lanes x 9 bits = 36 bits (`ScaleFactorMem.scala:12-14,304-330`); addressed by `write_addr & ~0xf` (`AccumulatorMem.scala:136-138`) and a k-block counter that advances every `tilesPerMxBlock = 32/DIM` k-tiles (`ScaleFactorMem.scala:194-202`).
6. Read-out: `AccumulatorScale` has an MX branch that hands the accumulated (already scaled) BF16 to the requantizer; there is no multiplicative output scale on that path (`AccumulatorScale.scala:155-177`).

### 4.2 What NVFP4 delivers
- `NvFp4Mesh.out_b(c)`: **`Vec(4, SInt(13))` = 52 bits per column**, exact, same lane order (so the repack at `ExecuteController.scala:1236-1257` still works with lanes sign-extended to 16 bits, 64 bits per entry).
- Value range: `|isum| <= 2304` for one K = 16 block (one pass).

### 4.3 Consequences
- **No rounding / no FP in the array**: `withWidthOf(accType)` at `ExecuteController.scala:1230` must become an int13 -> 16-bit sign-extend (or the write bundle carries the raw 13-bit lanes).
- **The scale stage (D3) sits at `AccumulatorMem.scala:211-263`** (between `pipelined_writes(0)` and the adder), replacing `applyE9M0Scale`: stage 0 `sA*sB` (4x4-bit significands + exponent add, can run in `ScaleFactorMem` where `multiplyScalesE8M0` is now, `:227-230`); stage 1 `isum(13b) x 8b` -> 21 bits; stage 2 pack to FP32 with no rounding. `acc_latency >= 2` is required today (`:196`); the new stage is deeper (3 steps), so the latency accounting (`acc_latency`, `pipelined_writes`) needs a bump.
- **Widths change**: scale response per column grows from 36 bits (4 x 9) to about 64-72 bits (4 x (8-bit significand product + exponent)); the accumulator entry grows from 4 x 16 to 4 x 32 bits (D4), i.e. `AccumulatorWriteReq.data` carries a different width **before** the scale stage (int lanes) than the SRAM stores **after** it (FP32 lanes). `AccumulatorMem.scala:43-49,127-134` and the SRAM wrapper (`:341-348`) assume one type `t`.
- **The accumulate `+` becomes an FP32 add** (`Arithmetic` instance for the new accumulator type; `hardfloat` `AddRecFN` is available, `Arithmetic.scala:9`). It is the only rounding in the pipeline, once per K block, matching the refmodel's float32 order.
- **Tensor scale (D6)**: `acc_scale` (CONFIG_EX) is applied at mvout through `AccumulatorScale`'s `scale_func`; MX currently bypasses that (`AccumulatorScale.scala:155-177`), so the NVFP4 build must keep the legacy non-MX read path (`:178-200`) or add the multiply to the MX branch.
- **D5 hardcodes**: `ScaleFactorMem.scala:196` and `LoopMatmul.scala:1106` (both `32 / DIM`; note D5 cited `LoopMatmul.scala:1118`, which is not that line in this checkout) become `scaleSize / DIM`. `GemminiConfigs.scala:239-240` already derives `tilesPerMxBlock = scaleSize / DIM`; libgemmini hardcodes `GROUP = 32` (`gemmini.cc:1442`) and the rocc-tests assume 32.

## 6. Recommendation
1. **Option (iii), an NVFP4-only config** for 6.1-6.5. Reasons: D4 and D5 change the accumulator and scale-block assumptions that MX modes depend on; (iii) keeps the Berkeley config untouched and buildable; the seam is small because `NvFp4Mesh` already has `Mesh`'s port shape and `MeshWithDelays` already produces the skew it needs; the integer array removes the float adders from the PE.
2. Seam to implement in Phase B: `MeshWithDelays.scala:187` picks `NvFp4Mesh` for the NVFP4 type; `ExecuteController.scala:1230-1261` replaces the width conversion; the scale stage and FP32 adder go into `AccumulatorMem.scala:211-282` (M6.3).
3. Keep (ii) as a later extension only if D8 needs both formats in one build; building the two configs separately gives the same comparison data.
4. Phase B order: (a) type + Arithmetic stubs and config that elaborates with `NvFp4Mesh` and raw int lanes written to the accumulator (no scaling yet) and a Verilator test with an integer-sum mvout, the M4 pattern; (b) M6.3 scale stage and FP32 accumulate; (c) libgemmini mirror.

## 7. Open questions

**Decisions (user, 2026-10-17):**
- **Q1:** (iii) NVFP4-only config. MX stays buildable separately, and comparisons use two builds.
- **Q2/Q5:** the scale stage lives inside `AccumulatorMem`, replacing `applyE9M0Scale`. Reuse MX's scale-read timing, raise `acc_latency`, and re-check the RAW hazard path.
- **Q3:** `ScaleFactorMem` outputs raw E4M3 bytes, and the sA·sB multiply happens in the scale stage.
- **Q8:** Spike switches by build define (`libgemmini_nvfp4`, like `_dim8`/`_dim32`).
- **Q4, Q6, Q7** are engineering checks:
  - Q4 (scale addressing at `kScaleShift=0`) and Q6 (dummy precision lists) are verified in M6.3.
  - Q7 (`tile_latency`) is chosen at M6.5. The default stays 1, inherited from MX.

- **Phase B decisions (user, 2026-10-17):** IEEE FP32 in the accumulator SRAM, and the FP32 adder pipelined now (2 stages) with explicit RAW hazard handling.

Original questions:
1. Option (iii) vs (ii) for the final deliverable: is an NVFP4-only config acceptable, or must MX FP4 and NVFP4 share one build (D8 comparison runs could be done with two builds)?
2. Where does the width change happen: widen the accumulator write request to a pre-scale type (int lanes) plus a post-scale type (FP32 lanes) inside `AccumulatorMem`, or do the int -> FP32 conversion and scaling before the write queue (scale stage in `ExecuteController`)? The second keeps `AccumulatorMem` single-typed but moves the `ScaleFactorMem` read ahead of the accumulator write.
3. Does `ScaleFactorMem` output the product `sA*sB` (about 18 bits/lane, multiplier in the mem) or the two raw E4M3 bytes (16 bits/lane, multiplier in `AccumulatorMem`)? Affects response width and where the stage-0 multiplier is pipelined.
4. MX scale memory layout: E4M3 scales are 8 bits, so the byte layout is unchanged, but the K-block rate is 1 per 16 (one per pass, `tilesPerMxBlock = 1`). Confirm the bank/address math at `ScaleFactorMem.scala:127-136,194-206` and the loop unit (`LoopMatmul.scala:1518-1546`) is correct for `kScaleShift = 0` at DIM=16 (the code exists for DIM=32, where it is also 0).
5. Latency: the new scale stage deepens the accumulator pipeline; is raising `acc_latency` (or adding a pipeline stage between `ExecuteController` and `AccumulatorMem`) acceptable for the existing hazard logic (`AccumulatorMem.scala:118-120` already carries a TODO about read-after-write)?
6. Mesh-row precision: NVFP4 uses a flat 13-bit partial sum in all 16 rows (no ramp). `meshProdPrecisionList`/`meshAccPrecisionList` (`ConfigsFP.scala:271-276`) are required by the config class; confirm they can be set to dummies for the NVFP4 type without affecting `MeshWithDelays`' `max_simultaneous_matmuls` or the mesh tags.
7. `tile_latency`: NVFP4 inherits `tile_latency = 1` (2 registers per hop) from `defaultMxFPConfig`; the synthesis of the NVFP4 array shows what a 1-register hop costs (the mesh is parameterized, both are tested). Which to ship is a timing question for M6.5.
8. Spike: should the NVFP4 mode be a new libgemmini build define or a runtime state bit (`mx_act_fmt == 3`)? D7 fixes the verification order but not the switch.
