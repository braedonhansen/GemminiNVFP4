# M6.2 Phase A1 results: NVFP4 weight-stationary mesh

Date: 2026-10-17. Tools as in `hw/pe_variants/RESULTS.md` (Yosys 0.69+, Chisel 6.7.0, firtool 1.75.0, Verilator 5.022). Logs: `logs/m6.2.steps`, `logs/m6.2-mesh-*.log`, `logs/m6.2-synth/`.

## Design
`NvFp4Mesh(dim, tileLatency)` in `src/main/scala/nvfp4pe/NvFp4Mesh.scala`: dim x dim `NvFp4MeshPE` (c1/c2 weight double buffer around the V6 `NvFp4PE`), `Vec(4, SInt(13))` partial sums, `L = tileLatency+1` registers per hop on a, b, d, propagate and valid, same structure as Gemmini `Mesh.scala`/`PE.scala` (see `docs/M6.2-integration-plan.md`, section 1). Skew/de-skew is done by the testbench, not the module. Elaborate: `sbt "runMain nvfp4pe.ElaborateMesh <dir> <dim> <tileLatency>"`; generated SV for DIM=16 and DIM=4 (tileLatency 0) is in `generated/`.

## Tests (`NvFp4MeshSpec`, ChiselSim/Verilator; vectors from `refmodel/vectors/mesh_passes_d{4,16}.txt`, generated by `refmodel/vectors.py`, expected values from `refmodel/hw_dot.py:mesh_block_sums`)
One pass = one K block (K = dim): M = N = 2*dim outputs per pass. Passes run back to back in one simulation: pass q+1's weights are preloaded into the idle c1/c2 buffer while pass q computes, with `propagate` alternating (this is the preload/flip test).

| Test | passes | outputs checked | mismatches |
|---|---|---|---|
| DIM=4, tile_latency 0, back-to-back | 207 | 13,248 | 0 |
| DIM=4, tile_latency 0, 3 idle cycles between passes | 207 | 13,248 | 0 |
| DIM=4, tile_latency 1 (2 regs/hop), back-to-back | 207 | 13,248 | 0 |
| DIM=16, tile_latency 0: refmodel's 67 blocks (3 diagonal passes) + +2304/-2304/zeros/-0/alternating/checkerboard corner passes + 24 random | 34 | 34,816 | 0 |
| DIM=16, tile_latency 1, 2 idle cycles, first 12 passes | 12 | 12,288 | 0 |

The DIM=16 vectors contain both 13-bit extremes (+2304 and -2304; asserted in the test). Every one of the 67 refmodel blocks appears on a pass diagonal (pytest `test_mesh_passes_exact_and_cover_refmodel_blocks`).

Negative controls (scratch copies, repo untouched): (1) carry-in of the folded adder dropped (`Cat(x, s)` -> `Cat(x, 0.U)`): all 4 tests FAIL (mismatches per mesh run: 12,187 / 12,187 / 12,187 / 30,202 / 7,674 mismatches per run); (2) weight select flipped (`Mux(prop, c2, c1)` -> `Mux(prop, c1, c2)`): all 4 tests FAIL (mismatches per mesh run: 12,916 / 12,916 / 12,916 / 31,800 / 9,318).

## Synthesis (same `hw/pe_variants/synth_metrics.sh`; AIG = `synth -flatten; abc -g AND`, gates = `abc -g cmos2`, depth = `ltp -noff`, AND lvl = AND cells only)
| Design | AIG ANDs | NOTs | cmos2 gates | depth (ltp) | AND lvl | flops |
|---|---|---|---|---|---|---|
| `NvFp4PE` (M6.1, comb) | 773 | 695 | 1180 | 60 | 34 | 0 |
| `NvFp4Mesh` DIM=4, L=1 | 13,143 | 11,754 | 19,545 | 70 | 38 | 1,376 |
| `NvFp4Mesh` DIM=16, L=1 | 210,635 | 188,191 | 311,765 | 71 | 38 | 22,016 |
| per PE (DIM=16) | 822.8 | 735 | 1,217.8 | | | 86 |

- Per-PE logic is +6.4% over the bare PE (weight select mux on `prop`, enable muxes for c1/c2 and the pipes); depth rises 60 -> 71 because the weight mux sits in front of the decode. Flops per PE: 52 partial sum + 8 a + 8 d + 16 (c1, c2) + prop + valid + pipe valid bits = 86.
- DIM=16 with `tileLatency` 1 was elaborated (`generated` SV built in the scratch dir) but **not synthesized** (the cmos pass of the DIM=16 L=1 design was skipped for time; the flop count would double on the pipelined paths and logic stays the same).

## MX FP4 reference (for scale; MX tree untouched)
Source: a **copy** of `mxgen/src/main/scala` in `~/nvfp4-logs/m6.2-work/mx*`, elaborated with Chisel 6.7.0 (Berkeley builds with 6.6.0) and a tiny elaboration main (`logs/m6.2-mx.sh`, `logs/m6.2-mxpe.sh`). Config `MxConfig.fp4Only`, product format (4,4) as in `defaultMxFPConfig`, no LUT, latency 0. This is MxGen's own `MxFpMul` PE (2x2 FP4 outer product with per-lane FP add into the column), the cell that `mac_mx` instantiates (`Arithmetic.scala:626`).

| Design | AIG ANDs | NOTs | cmos2 gates | depth (ltp) | AND lvl |
|---|---|---|---|---|---|
| MX FP4 PE, acc (8,8) = BF16 (last mesh row) | 5,165 | 4,013 | 6,840 | 175 | 108 |
| MX FP4 PE, acc (4,5) (rows 0-7 of the ramp) | 3,494 | 2,768 | 4,842 | 142 | 84 |
| NVFP4 PE (V6 + 13-bit adders) | 773 | 695 | 1,180 | 60 | 34 |

- PE to PE: NVFP4 is 6.7x smaller than the BF16 MX PE (4.5x vs the smallest ramp row) with a depth of 60 vs 175 (142).
- 16 x 16 array, extrapolated (not measured): 256 x 5,165 = 1.32 M ANDs (BF16 rows) or 256 x 3,494 = 0.89 M (smallest ramp precision everywhere) vs 0.21 M measured for the NVFP4 mesh including its registers. The real Gemmini ramp (5/6/7/8-bit significands) lies between the two MX numbers.
- **Not done:** synthesis of the whole 16x16 MX `MxSystolicArray` (`logs/m6.2-mx.sh` elaborates it; the Yosys AIG pass had not finished after 35 min and was stopped). MxGen's array is also not Gemmini's mesh (no ramp, no per-hop valid gating, one accumulator format), and MX's per-hop registers are not in the per-PE rows above, so the PE rows (no flops) are the fair comparison.
- Caveat as before: AIG/gate counts are technology-independent proxies; differences of this size (4.5x-6.7x) are far outside the "not separable" band.
