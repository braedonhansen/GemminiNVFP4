# Brief: M7.A, accuracy study (FP32, INT8, MXFP8, MXFP4, NVFP4)

Follow `AGENT_LOOP.md`, including the rule that **a check must fail when it checked nothing**. Read first:
- `docs/M7-measurement-plan.md`: the "Configs compared" table and the whole "M7.A Accuracy" section. This brief implements that section.
- `refmodel/quant.py`, `refmodel/hw_dot.py`, `refmodel/formats.py`, `refmodel/tiny_transformer.py`, `refmodel/export_e2e.py`
- `PROGRESS.md` "Environment notes" for both trees

**Goal**: measure how accurately each design computes a matmul, against an FP64 matmul of the unquantized inputs. Do it at two levels:
- **F (format):** the format alone.
- **H (hardware):** each design's real arithmetic. Every Level-H model must be proven bit-exact against that design's own Spike model before its numbers are used.

**No RTL changes and no Verilator runs** in this task.

## Ground rules
- **Stock stays exactly stock.** FP32 and INT8 are upstream Gemmini in `~/chipyard` (8c3f9923). MXFP8 E4M3 and MXFP4 are the MX tree `~/chipyard-mx` (266c593f). NVFP4 is our branch.
  - Never edit source files in either tree.
  - Build outputs (e.g. a libgemmini `.so` or a test binary for a config the tree doesn't build by default) go under `~/nvfp4-logs/m7a/`, and you must record the exact build commands.
- **Quantization recipes.** Each format uses its own standard recipe:
  - **NVFP4:** the refmodel's existing recipe.
  - **MX:** OCP MX v1.0.
    - Shared exponent = floor(log2(block amax)) - emax_elem, with emax_elem = 2 for E2M1 and 8 for E4M3.
    - Block size 32, along K.
    - Elements are rounded RNE with saturation.
    - **Before relying on this, find out how the MX branch quantizes its own test data** (`gemmini-rocc-tests/fp4_matmul_model.py`, `fp8_matmul_model.py`, `golden_model.py`, the `gen_*.py` scripts). If it differs from OCP, report both and use the branch's recipe for Level H.
  - **INT8:** per-tensor symmetric scale = amax/127, RNE, clamp to [-127, 127].
  - **FP32:** cast to float32.
- **Python models in the MX repo** (`fp4_matmul_model.py`, `fp8_matmul_model.py`, `golden_model.py`, torch-based) may already mirror the MX hardware.
  - You may **call** them in place, or port their logic into `refmodel/mx.py` with a header comment crediting the source (BSD 3-Clause, UC Regents).
  - Don't copy files wholesale into this repo.
  - Either way, Spike is the judge of bit-exactness.
- Everything in `refmodel/` must be vectorized numpy. K=16384 at 64x64 with 10 seeds has to run in minutes, not hours. If torch is needed only to call the MX models, use it from WSL's conda env and don't add it to `requirements.txt`.

## If something doesn't match
- If a Level-H model mismatches Spike, print the first 8 mismatches with their (i, j) indices and the bit patterns, and find the cause.
  - Up to 3 targeted fixes to **the Python model** are allowed.
  - Never change Spike, the RTL or the stock trees to make them agree.
  - If it's still unresolved, mark that design's Level H "unverified", keep its Level F results, and report it.
- If the refmodel's NVFP4 path disagrees with Spike, STOP and report. It was bit-exact through M6.5.
